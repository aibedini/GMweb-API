# GMweb encrypted replication: V1 baseline and V2 contract

Feature ID: `multi-device-replication-v2`. Status: V2 design; V1 remains the active wire protocol until implementation, Android fixture alignment and physical acceptance.

## Ownership and identity

Android owns telephony observation and irreversible modem submission. GMweb owns the opaque event sequence, encrypted current state, per-device authorization and durable commands. A browser owns its local encrypted replica and decryption keys. The authenticated agent identity, not a request-body `sourceDeviceId`, identifies an uploader.

`eventId` is generated by the producer and stable across retries. `serverSequence` is allocated by GMweb per account. A browser's event cursor is the latest sequence whose ciphertext and cursor were committed together locally. Decryption progress never changes that cursor.

## Current V1 API

| Operation | Route | Current behavior |
|---|---|---|
| Android event upload | `POST /api/v1/agent/events/batch` | Validates the whole batch, allocates per-account sequences for accepted events, returns `accepted[]` and a duplicate count. A repeated identical event returns its original sequence in `accepted[]`. |
| Browser delta | `GET /api/v1/sync?after=&limit=` | Ordered ciphertext, `nextCursor`, `hasMore` and replica metadata; stale retained cursor returns `snapshot_required`. |
| Initial encrypted state | `GET /api/v1/web/bootstrap` | V1 first-page bootstrap retained for older consumers. The current PWA uses the V2 snapshot session instead. |
| Additional state | `GET /api/v1/web/conversations`, `GET /api/v1/web/conversations/:conversationId/messages` | Keyset pages of mutable encrypted current state. They are not an immutable V2 snapshot session. |
| Key recovery | `GET /api/v1/linked-device/key-grants`, `GET /api/v1/linked-device/keyring` | Browser-targeted opaque grants, separately fetched from the normal event cursor. |
| Client ACK | `POST /api/v1/web/sync/ack` | Reports a committed browser event cursor with generation and snapshot version. |
| Web command | `POST /api/v1/commands` | Durable idempotency-keyed command; `GET /api/v1/commands/:id` reports state. |
| Agent claim | `POST /api/v1/agent/commands/claim` | Atomic queued-to-delivered claim. A timed lease and reclaim contract are not yet present. |
| Realtime hint | `GET /api/v1/sse` | Contentless invalidation; the browser re-pulls delta by cursor. |

## V2 additive contract

Implemented ingest slice: `POST /api/v1/agent/events/batch-v2` returns one indexed result per item: `ACCEPTED`, `DUPLICATE` with its original sequence, `CONFLICTING_DUPLICATE`, or `INVALID_EVENT` with a safe error code. The response includes the committed account `highWatermark`. The route binds source identity from agent authentication, not request body. V2 is not advertised as the preferred protocol until browser and command contracts are complete.

Implemented snapshot: `POST /api/v1/web/snapshot-v2` creates a device-bound, hour-lived snapshot session in one SQLite transaction at `baselineSequence`. Immutable ciphertext conversation, message and contact state is stored in SQLite and has been verified across a connection reopen; independent process-death acceptance is NOT RUN. `GET /api/v1/web/snapshot-v2?token=&cursor=&limit=` continues its ordered pages; each response repeats baseline, generation and expiry. The PWA now stores each page and its cursor atomically in IndexedDB, resumes incomplete sessions, restarts expired ones, and begins delta from the baseline only after the final page commits. Its local event cursor is not advanced while a snapshot is incomplete. V1 endpoints remain available to older consumers.

Compaction is capped at the lowest baseline of an active, same-generation snapshot session. It cannot prune that session's post-baseline delta until the session expires or is superseded by a new replica generation; the snapshot rows themselves are retained until expiry cleanup.

V2 will expose explicit protocol capabilities and retain every V1 endpoint during transition. A batch response has one result per item: `ACCEPTED`, `DUPLICATE` with original sequence, or a safe rejection code. A rejected item consumes no sequence. Batch-level errors are reserved for malformed framing, authorization failure or exceeded batch limits.

A V2 snapshot starts with a server-issued token, `replicaGeneration`, immutable `baselineSequence`, expiry and first page. Continuations use that token and a keyset cursor. The final page marks `snapshotComplete`. Browser storage keeps `snapshotCursor`, `eventCursor`, `keyCursor` and `projectionCursor` separately. The browser begins delta catch-up from `baselineSequence` only after all snapshot pages have committed. If a token expires or generation changes, it starts a new snapshot while preserving device identity.

Key-grant failures mark key sync degraded; valid ciphertext remains receivable and storable. Locked content distinguishes missing key, unsupported crypto version and failed decryption. A later authorized grant retries affected local content.

Commands preserve `commandId`, idempotency key and `clientMessageId` across response loss and worker recovery. A bounded worker lease permits reclaim without creating a new logical command. Android must independently dedupe irreversible modem submission by that identity before any exactly-once physical claim is possible.

## Safe error vocabulary

Existing V1 codes such as `snapshot_required`, `capability_denied`, `encrypted_payload_required`, `unsupported_schema_version`, `unsupported_crypto_version`, `invalid_payload_encoding` and `event_payload_too_large` retain their current meaning. V2 adds item-scoped rejection and snapshot-token expiry codes only when the corresponding implementation and OpenAPI are introduced. Error responses and diagnostics contain no SMS body, recipient, plaintext preview, private key or credential.

## Compatibility and rollout

1. Deploy additive GMweb schema and V2 routes with V1 still active.
2. Deploy Web support with an explicit capability check and reversible frontend rollout.
3. Deploy Android with the same feature ID and byte-checked contract fixtures.
4. Activate V2 only after both sides pass contract tests; retain V1 fallback during transition.
5. Complete controlled physical acceptance before making V2 default. Synthetic 360k tests are labeled synthetic.

Rollback retains additive database columns, encrypted rows and browser identity. Do not clear IndexedDB or downgrade stored ciphertext to plaintext as a recovery tactic.
